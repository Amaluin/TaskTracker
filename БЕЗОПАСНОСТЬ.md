# 🔒 Безопасность базы данных

## ⚠️ Текущая ситуация

Вы правы! Текущие RLS политики **слишком открытые**:

```sql
CREATE POLICY "Enable all operations for tasks"
  ON tasks FOR ALL
  TO anon, authenticated
  USING (true)  -- ← Разрешает ВСЁ всем!
  WITH CHECK (true);
```

**Проблема:** Любой пользователь с Anon Key может:
- Читать все задачи всех пользователей
- Изменять чужие задачи
- Удалять чужие данные

---

## 🎯 Почему так сделано?

Ваше приложение **не использует** встроенную аутентификацию Supabase (`auth.uid()`), а управляет пользователями на стороне клиента через поле `user_id`.

**Текущая архитектура:**
```
Flutter App → Supabase (anon key) → База данных
     ↓
  user_id (строка, генерируется в приложении)
```

**Проблема:** Supabase не знает, кто текущий пользователь, поэтому не может фильтровать данные на уровне БД.

---

## ✅ Решения (3 варианта)

### Вариант 1: Базовая защита (быстро, минимальные изменения)

**Что делает:**
- Разрешает операции только для `anon` роли
- Фильтрация по `user_id` остается на стороне клиента
- Добавляет валидацию `user_id`
- Добавляет rate limiting

**Плюсы:**
- ✅ Не требует изменений в Flutter приложении
- ✅ Быстро применяется
- ✅ Защита от базовых атак

**Минусы:**
- ❌ Технически любой может получить доступ к чужим данным
- ❌ Зависит от правильной реализации на клиенте

**Применение:**

**Уровень защиты:** 🟡 Средний

### Вариант 2: Строгая защита с API ключами (рекомендуется)

**Что делает:**
- Создает таблицу `api_keys` для каждого пользователя
- Проверяет API ключ в каждом запросе
- Фильтрует данные по `user_id`, связанному с ключом

**Архитектура:**
```
Flutter App → API Key (уникальный для пользователя) → Supabase → БД
                ↓
          Проверка в RLS политике
                ↓
          Доступ только к своим данным
```

**Плюсы:**
- ✅ Каждый пользователь имеет уникальный ключ
- ✅ Невозможно получить доступ к чужим данным
- ✅ Можно отозвать ключи
- ✅ Можно установить срок действия

**Минусы:**
- ❌ Требует изменений в Flutter приложении
- ❌ Нужно управлять ключами

**Применение:**

1. **В SQL Editor:**
```sql
-- Раскомментируйте ВАРИАНТ 2 в database_security.sql
```

2. **В Flutter:**
```dart
// Генерация API ключа для пользователя
final apiKey = await generateApiKey(userId);

// Сохранение в SharedPreferences
await prefs.setString('api_key', apiKey);

// Использование в запросах
final response = await supabase
  .from('tasks')
  .select()
  .headers({'x-api-key': apiKey});
```

**Уровень защиты:** 🟢 Высокий

---

### Вариант 3: Максимальная защита с Supabase Auth (лучшая практика)

**Что делает:**
- Использует встроенную аутентификацию Supabase
- Автоматическая проверка `auth.uid()`
- Полная изоляция данных пользователей

**Архитектура:**
```
Flutter App → Supabase Auth (email/password) → JWT Token → БД
                                                    ↓
                                            auth.uid() в RLS
                                                    ↓
                                        Автоматическая фильтрация
```

**Плюсы:**
- ✅ Максимальная безопасность
- ✅ Встроенная аутентификация (email, OAuth, и т.д.)
- ✅ Автоматическое управление сессиями
- ✅ Лучшая практика Supabase

**Минусы:**
- ❌ Требует полной переработки аутентификации в приложении
- ❌ Нужно изменить `user_id` с TEXT на UUID

**Применение:**

1. **В SQL Editor:**
```sql
-- Раскомментируйте ВАРИАНТ 3 в database_security.sql
```

2. **В Flutter:**
```dart
// Регистрация
await supabase.auth.signUp(
  email: email,
  password: password,
);

// Вход
await supabase.auth.signInWithPassword(
  email: email,
  password: password,
);

// Запросы (автоматическая фильтрация по auth.uid())
final tasks = await supabase
  .from('tasks')
  .select();  // Вернет только задачи текущего пользователя
```

**Уровень защиты:** 🟢🟢 Максимальный

## 🆘 FAQ

### Q: Насколько опасны текущие политики?

**A:** Зависит от контекста:
- **Разработка/тестирование:** Приемлемо
- **Production с реальными данными:** ⚠️ Опасно
- **Публичное приложение:** 🔴 Очень опасно

### Q: Что может сделать злоумышленник?

**A:** С текущими политиками:
1. Получить Anon Key из приложения (декомпиляция)
2. Написать скрипт для доступа к API
3. Читать/изменять/удалять все данные всех пользователей

### Q: Как быстро исправить?

**A:** 
1. Примените `database_security.sql` (ВАРИАНТ 1) - 5 минут
2. Для production - внедрите ВАРИАНТ 2 или 3

### Q: Нужно ли менять Flutter код?

**A:**
- ВАРИАНТ 1: ❌ Нет
- ВАРИАНТ 2: 🟡 Минимально (добавить API ключ в заголовки)
- ВАРИАНТ 3: ✅ Да (полная переработка аутентификации)
